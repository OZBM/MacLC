## Rejected work

An earlier agent run for handoff item 5 fabricated a CoreVideo constant:

```c
#define kCVPixelFormatType_420YpCbCr16BiPlanarVideoRange 'sv20'
```

No such format exists. The SDK defines 16-bit biplanar YCbCr for 4:2:2
(`'sv22'`) and 4:4:4 (`'sv44'`) only, and nothing for 4:2:0. The whole patch was
discarded. A follow-up run also proposed mapping an `'sv22'` or `'sv44'` buffer
to `VLC_CODEC_CVPX_P010`, which would hand downstream code the wrong
subsampling and plane geometry; that hunk was removed too. What survives is the
corrected comment in `4cf0014`.

The lesson generalises: treat any platform constant introduced by an agent as
unverified until it is found in a real SDK header.

That probe was finished, corrected, compiled and run in this session. It is now
`tools/hdr-probe/vt_probe.m`, with its first run recorded in
`tools/hdr-probe/RESULTS.md` (commit `3f55357`).

As written, its pixel-format section was structurally inconclusive: it built a
`CMVideoFormatDescription` with no parameter sets, which no decoder accepts, so
every format failed identically with OSStatus -8971. It now hardware-encodes one
HEVC Main10 frame and probes against the description the encoder itself
produces, and says so explicitly when it has to fall back.

### What is now measured rather than assumed

- The development machine is an **Apple M3 Max (Mac15,9) on macOS 26.2**.
- `VTIsHardwareDecodeSupported(kCMVideoCodecType_AV1)` returns **YES** here, so
  every condition in `deviceSupportsAV1()` holds and the hardware AV1 path is
  reachable on this machine. Handoff item 6 no longer needs different hardware;
  it needs an AV1 HDR stream.
- Dolby Vision HEVC (`'dvh1'`) also reports hardware decode support, which is
  worth weighing against the RPU parser work: VideoToolbox may already be doing
  some of this internally.
- VP9 has no hardware decode here.
- A decompression session for an HEVC Main10 source accepts **`'sv22'` (4:2:2
  16-bit) and `'sv44'` (4:4:4 16-bit)** destinations. This changes the shape of
  handoff item 5: a genuine >10-bit path does exist, it simply cannot be 4:2:0,
  and would rely on VideoToolbox for the chroma upsampling.
- The built-in display reports an EDR headroom of **2.951** against a potential
  of **16.0**. The EDR handling, the subtitle attenuation curve and the dynamic
  range switching are therefore all observable on this machine, contrary to what
  the original handoff assumed.

## Third pass: adversarial review, and what it found

With the delegation quota restored, the review that had failed twice finally
ran. It found nine defects in the commits up to `ca1c518`, every one of which I
re-confirmed by reading the code before acting on it. Two were critical:

- `prepareDisplay` set `isPreparingDisplay` and never cleared it, so a single
  failed or slow layer creation permanently disabled retries and left
  `getOrWaitDisplayLayer` burning its full one-second timeout on every frame.
  Playback would have run at one frame per second.
- The `dispatch_sync` I had introduced in `close` deadlocks by construction: VLC
  tears the display down from the main thread, which is already blocked in
  `vlc_join()` on the vout thread (`src/video_output/video_output.c:2100`).

The rest: 1080p HDR tagged BT.709 because the HDR test sat inside the UHD
branch; BT.709 video tagged as sRGB in `caopengllayer`, which is the wrong tone
response on the majority of all playback; Dolby Vision matrices destroyed when
`dm_compression` is set; an unbounded skip in the HDR10+ SEI parser; a
desynchronising extension block; and an HLG stream with partial mastering data
producing a zero-nit volume.

One of those was mine to own: the `kCGBitmapByteOrder32Host` I had asked for was
a regression. `VLC_CODEC_ARGB` is documented as ARGB in memory address order,
and on a little-endian machine `32Host` makes CoreGraphics read the word as
B, G, R, A. Red and blue were swapped on every subtitle. It is `32Big` now.

All nine are fixed (`8a50b00`, `54dd2b7`, `28df664`, `3a1d775`).
