## Verification actually performed

- Every modified source compiles in the existing autotools build directory
  (`build/`, configured with `--enable-videotoolbox --enable-macosx`). The only
  link failure in a full `make` is `liblibbluray_plugin` failing to find
  `library 'intl'`, which predates this work and is unrelated.
- `test/src/video_chroma/copy_neon.c`: 3888 configurations, 0 guard violations,
  0 mismatches, `RESULT: PASS`.
- `test/src/misc/cvpx_hdr_metadata.c`: all five cases pass, including the two
  added in `a1a6d37`.
- Both new test cases were run against the pre-`8aaa5f6` `vt_utils.c` and both
  fail there, so they are genuine regression coverage rather than tests written
  to match the new code.

Both test binaries had to be compiled and linked by hand: `automake` is not
installed on this machine, so `test/Makefile.in` cannot be regenerated and the
autotools targets for these two suites do not exist in the configured build
directory. The Meson registration in `41c7ba0` could not be exercised either —
neither `meson` nor `ninja` is installed here.

## Rejected work

An earlier agent run for handoff item 5 fabricated a CoreVideo constant:

```c
#define kCVPixelFormatType_420YpCbCr16BiPlanarVideoRange 'sv20'
```

No such format exists. The SDK defines 16-bit biplanar YCbCr for 4:2:2
(`'sv22'`) and 4:4:4 (`'sv44'`) only, and nothing for 4:2:0. The whole patch was
discarded. A follow-up run also proposed mapping an `'sv22'` or `'sv44'` buffer
to `VLC_CODEC_CVPX_P010`, which would hand downstream code the wrong
subsampling and plane geometry; that hunk was removed too. What survives is the
corrected comment in `4cf0014`.

The lesson generalises: treat any platform constant introduced by an agent as
unverified until it is found in a real SDK header.

## Still open

- **Item 6, hardware AV1 on M3/M4.** Needs the hardware and 10-bit AV1 HDR
  streams. Untouched.
- **Item 5, a real >10-bit path.** Would mean new VLC fourccs for semi-planar
  4:2:2 and 4:4:4 16-bit, the matching copy and SIMD routines, and chroma
  resampling, since a 4:2:0 bitstream does not map onto either format. Not
  started.
- **Dolby Vision RPU.** The parser in `3a90e9e` is written against FFmpeg's
  `dovi_rpudec.c` and fails non-fatally on any inconsistency, but it has never
  seen a Profile 5 or Profile 8.1 stream. Treat it as unproven.
- **HDR10+ SEI extraction.** Same caveat: no stream with ITU-T T.35 SEI has been
  played through it.
- **`pl_scale` render target.** The output colour space and display peak are
  still unset, so libplacebo tone-maps against default assumptions. A TODO marks
  the spot. Fixing it needs display characteristics the filter cannot currently
  see.
- **ICC profile source.** Taken from the main display, not the window's own
  screen, because reaching the attached `NSScreen` from `libplacebo/display.c`
  needs AppKit plumbing that does not exist there.
- **Independent adversarial review.** A read-only audit of this whole delta was
  launched and did not complete: the Gemini account hit its quota. Worth
  re-running, with particular attention to the two new bitstream parsers and to
  the threading changes in `VLCSampleBufferDisplay.m`.

## Nothing here has been seen on a screen

No playback, no HDR display, no photometry. Every behavioural claim above is
compile-and-unit-test grade. The subtitle curve, the EDR headroom handling, the
compositor's tone response and both new parsers all need an Apple Silicon Mac
with an EDR-capable panel and real test media before they can be called correct.
